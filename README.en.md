Robot code maintained by FIRST® Robotics Competition team [**12363 LEOMOTIVE**](https://github.com/LEOMOTIVE-12363) for the 2026 game **REBUILT**. Built on **Alphabots 8810's robot and open-source code**, this is LEOMOTIVE's own version, with ongoing development and improvements by our team. Technical foundation: Java 17 · WPILib command-based · AdvantageKit TalonFX swerve template.

> **Project ownership and upstream origin**: this repository is **12363 LEOMOTIVE's independently maintained derivative**. **8810 Alphabots** provided the original robot and upstream code. Forked from [Alphabots-8810/8810-2026-offseason](https://github.com/Alphabots-8810/8810-2026-offseason), `main` retains the upstream competition-code baseline plus this fork's licensing, documentation, and repository-hygiene changes. `demo` hosts LEOMOTIVE's current teleop-only demo development. See [Branch model](#branch-model).

## Highlights

The following capabilities come from the upstream competition code retained on `main`. LEOMOTIVE currently develops and improves its teleop-only demo version on `demo`; see the branch model for each branch's scope:

- **Swerve drivetrain** — CTRE TalonFX + Pigeon 2, hardware constants generated by CTRE Tuner X (`generated/TunerConstants`), high-frequency Phoenix odometry thread, built-in SysId routines
- **FUEL handling chain** — deployable intake (position-controlled arm + roller) → hopper / indexer (CANrange ball detection) → Drum shooter + adjustable Hood
- **Tactical software** — HUB shooting (including shooting on the move), neutral-zone Ferry lobbing, Trench traversal (driver-assist + fully automatic via [Autopilot](https://github.com/therekrab/autopilot))
- **Vision** — Limelight (MegaTag2) global pose estimation fused into swerve odometry
- **AdvantageKit three-mode architecture** — REAL / SIM / REPLAY share one codebase, with deterministic log replay
- **maple-sim desktop simulation** — 2026 REBUILT arena (HUB / Trench collision geometry) physics sim
- **Custom Elastic dashboard** — layout versioned in `elastic-layout-1027.json`, plus NetworkTables tuning scripts `scripts/nt_tune.py` / `scripts/pid_analysis.py`

## Demo controller roles

Driver Station port **1 takes priority over 0** for both driving and every button. While port 1 is connected, port 0 inputs are ignored; disconnecting port 1 falls back to port 0. With neither connected, drive inputs are zero. These are Driver Station slots, not physical USB sockets.

| Function | Port 1: simplified demo | Port 0: full controls |
|---|---|---|
| Drive / turn | Left stick / right-stick X | Same |
| Intake / eject / shoot | LT / LB / RB | LT / RT / RB |
| Heading snap (tap) | D-pad up / down / left / right | Y / A / X / B |
| D-pad low-speed crawl (toggle latch) | Unbound | Up / down / left / right at 10% of maximum linear speed |
| Reset heading (blue 0° / red 180°, position kept) | B | Start |
| Retract intake | Unbound | LB |
| Current-feed / outward zeroing | Unbound | No physical binding; commands retained |
| Cycle LED themes / idle effects | Back / Start | No LED switching |
| Reset simulated field | Unbound | No physical binding |

A short D-pad press on port 1 or XYBA press on port 0 starts an automatic heading snap (2026-10-29, see `docs/decisions/0030`; 0028 retains the historical mapping). Red alliance adds 180° to every blue target, preserving the same driver-relative directions without an additional left/right mirror:

| Direction | Port 1 input | Port 0 input | Blue target | Red target |
|---|---|---|---:|---:|
| Forward (intake forward) | Up | Y | 0° | 180° |
| Toward driver (intake backward) | Down | A | 180° | 0° |
| Intake left | Left | X | 90° | −90° |
| Front right | Right | B | −90° | 90° |

Releasing the D-pad or XYBA does not cancel the turn. The command finishes when the existing angle PID reaches its goal, then returns to the default joystick drive. Moving right-stick X beyond the existing deadband cancels the snap immediately and restores manual rotation; disconnecting the source controller or taking away its priority also cancels it. This rotates the chassis without resetting position or odometry.

Only port 0 uses real POV edges for a toggle-latched low-speed crawl (2026-10-29, see `docs/decisions/0031`): with no latch active, a cardinal press starts field-relative translation in that direction at 10% of maximum linear speed, and **releasing the D-pad does not stop it**. A fresh same-direction or opposite-direction press on the same axis stops the latch; perpendicular presses are ignored completely (up/down does not affect a right latch). The original left-stick ×0.9 translation inputs add to the latched offset, while right-stick X independently controls rotation; neither stick cancels the intent, and centered sticks leave exactly the original 10% command. Another Drive command may temporarily borrow the drivetrain, after which the same latched command resumes without blindly preempting the borrower. Disable, disconnect, or priority loss clears the intent and stops; reconnecting or regaining control never restarts it, and a POV held while disabled does not start on enable. The path reuses startup steer alignment, straight-line heading hold, red-alliance translation flip, and Dashboard limits. Inverting the existing deadband range rescale makes the squared normalized command exactly 0.1 rather than bypassing the limits or changing the deadband.

The displaced port-0 operations—current-feed (formerly A) and outward zeroing (formerly Y)—receive no new physical bindings. Their commands and direct-scheduling paths remain available, and `Manual` likewise remains implemented with no controller binding. Port 0 LB now runs inward intake homing, while port 0 RT runs complete outtake; the former RT local reverse is removed. Port 0 Start matches port 1 B: blue resets heading to 0°, red to 180°, position is preserved, and reset works while disabled. The former Start simulated-field reset has no physical binding. Port 0 B remains the right-heading snap, while port 1 B reset and all other DS1 behavior are unchanged.

On port 1, Back cycles the five themes in the order Marigold Bridge → Festival Night → Papel Fiesta → Alebrije Glow → Candle Memory, and Start cycles the five idle effects in the order Static → Breathe → Slow Flow → Chase → Color Step; each press advances exactly one item. Both operate the existing `LED Pattern` / `LED Idle Effect` choosers, so a change from either the controller or Elastic is reflected as the actual selection on the other side and saved by the existing power-cycle persistence. Changing themes still preselects the recommended idle effect, which can then be overridden with Start or Elastic. From Off or a standalone pattern, Back enters Marigold Bridge while Start leaves both selections unchanged. Port 0 Back is unbound, and port 0 Start only resets heading; it does not switch LEDs.

LT is a toggle (since 2026-10-26; the latch became an independent intent on 2026-10-27, see `docs/decisions/0023`): one press extends the intake and starts continuous collection, and a second press stops collection (the intake stays extended, no auto-retract); mechanism commands like shooting merely borrow the shared subsystems — when they finish, collection resumes automatically and the latch is unaffected; a robot disable or the controlling pad disconnecting/losing priority stops it the same way, and it never resumes on its own; if LT was still held when it stopped, the operator must release LT and press it again — control returning by itself is not a new press (real button-edge detection since 2026-10-27, see `docs/decisions/0022`). Holding the outtake input (RT on port 0 or LB on port 1) first stops any running collection, then reverses the complete feed path; releasing it stops the reversal and collection does not auto-resume. Full reverse is momentary: while port 0 holds RT or port 1 holds LB, the intake roller, indexer, and feeder all reverse, and the requests zero on release, disconnect, priority loss without the new owner holding the corresponding outtake input, or disable. The old port-0 RT local reverse is removed, and port-0 LB instead runs inward intake homing. The bindings take no subsystem ownership, so a concurrently running shooting loop overwrites the reverse writes (original behavior, intentionally unchanged).

## Startup steer alignment & straight-line heading hold

(2026-10-28, see `docs/decisions/0029`) A **translation** command starting from genuine rest (including a full-stick launch) first rotates the four steer wheels to their target angles while the drive motors hold off; drive releases once all four are aligned (5-degree tolerance, drive-reversal aware) and unconditionally after at most 1 second, so a steer failure can never wedge the drivetrain. The gate serves translation starts only: **manual rotation has absolute priority and is never delayed** — pure-rotation starts and translation-plus-manual-rotation starts bypass it entirely. A direction change at speed, even through a one-loop zero command, is judged by the measured chassis speed as "still rolling" (rest thresholds 0.20 m/s / 0.40 rad/s, chosen from measured margins, see 0029) and adds no wait — it keeps the ordinary cosine-scaled transition — and a robot disable resets the gate so a re-enable is judged against the actually rested robot. A fully parked robot (no translation, no rotation input) never turns itself. A right stick deflected past the existing deadband keeps absolute manual rotation priority; once it recenters with translation present, the gyro holds the target heading in closed loop (reusing the existing `ANGLE` PID constants). Releasing the right stick adopts the heading at that moment — no spring-back — and while parked, on command restart (including disable/re-enable), and after the port-1 B heading reset, the CURRENT heading is always the target, never a stale one. New read-only log keys: `Drive/StartupAlignHold`, `DriveCommands/HeadingHoldActive`, `DriveCommands/HeadingHoldTargetDeg`. Deadbands, CANcoder offsets, motor gains, NetworkTables keys, and the Elastic layout are unchanged. Verified in desktop simulation; real-robot steer response, rest thresholds, and hold feel await a robot run.

## Operator panel & at-speed feed gating

While the robot is enabled and the button's controller has control priority, holding a shoot button first drives Drum and Hood to their Elastic targets and **waits for measured flywheel speed within ±3.0 rot/s of the limited target for 0.15 s before initial feeding** (see `docs/decisions/0021` for the tolerance change): RB on either port (`Shooting(false)`, velocity feed) and directly scheduled `Shooting(true)` (50 A Indexer/Feeder requests) share this startup gate, so a full hopper is not pushed against an accelerating flywheel. The `Manual` command retains the same startup gate against its own 50 rot/s target, but currently has no controller binding and can only be scheduled directly in code. **Feeding continues after a normal release (2026-10-27, see `docs/decisions/0024`)**: per-ball speed variation and nonzero target edits no longer create a stop/start cycle, while Drum and Hood keep tracking their targets; this is not a per-loop at-speed interlock for the whole volley. Setting `Flywheel Speed Limit (%)` to 0 still stops feeding immediately and revokes the permit; restoring a positive value requires the speed window again unless the timeout latch is active, and the latch never crosses 0%. **3 s force-feed timeout**: accumulated below-speed waiting at startup or recovery at a positive limit force-feeds for the rest of the press once it reaches 3 s, latching off the speed gate until release (Elastic `Force Feed Timeout (s)`, default 3 s, clamped to 0.5–10 s and power-cycle persistent, see `docs/decisions/0022`); feeding, 0%, and UNJAM pause rather than clear the accumulator. Hood position only logs a diagnostic and never gates feeding. These paths use no vision, AprilTags, pose, or aiming data. Release, disconnect, priority loss, interruption, or disable still stops the command and feed; Drum coasts on release/disable and never restarts merely because the robot is re-enabled (see `docs/decisions/0015`). The hood is likewise no longer auto-zeroed when shooting ends: on release or disable it keeps the latest Elastic target, and the enabled idle follower keeps applying the newest target (Manual's own target and the outward-zeroing commands themselves are unchanged, see `docs/decisions/0025`).

Automatic jam clearing keeps its existing reverse outputs and duration (0.5 s back-off), but its confirmation now requires stall evidence instead of current alone (2026-10-28, see `docs/decisions/0027`): UNJAM is confirmed only when the stator current stays above 90 A **and** the measured speed stays near zero (|speed| < 5.0 rot/s, a preview bound) for the full 0.2 s window, and any loop at healthy speed resets that window — high current at healthy speed (|speed| ≥ 5.0 rot/s) no longer triggers the reverse. The retract timer remains frozen during 0% pauses and UNJAM. When the back-off finishes, the still-active command resumes feeding through the same at-speed gate: if the flywheel sagged during the stall it must re-reach speed and re-earn the stable window first, so balls are never pushed straight back into a slowed flywheel (with the force-feed latch active, the post-unjam volley resumes feeding directly).

`Robot Action`, `Feed Allowed`, and `Feed Blocked Reason` continue to report the command's actual feed decision; while feeding waits, `Robot Action` shows `Spinning Up` and the blocked reason is one of `Flywheel not at speed` / `Stabilizing shot` / `Flywheel limit is 0%`; after the timeout the panel shows plain `Feeding` like a normal volley; `hoodReady` remains a measurement-based diagnostic. The Elastic demo page shows read-only operator status:

- `Robot Action` / `Feed Allowed` / `Feed Blocked Reason`
- `Drum Target Speed (rot/s)` / `Drum Actual Speed (rot/s)`

Two stutter-related fixes address different failure paths, and both require a fresh deploy and on-robot verification: `docs/decisions/0024` (#74) removed the per-loop at-speed gate after a normal release, eliminating gate-induced feed pauses; `docs/decisions/0027` corrected the UNJAM evidence — previously, sustained high current tripped the 0.5 s reverse even while the indexer was still turning, whereas now stator current above 90 A **and** |speed| below 5.0 rot/s must hold for 0.2 s. Neither claims to eliminate every mechanical jam or every possible stutter: a jam that keeps the indexer crawling at or above 5.0 rot/s will not auto-clear (use 0%, release, or manual reverse), and 5.0 rot/s is a preview bound — no real current/velocity traces have been collected yet. After redeploying, retest 25% and 50% with the same ball count: high current at healthy speed (|speed| ≥ 5.0 rot/s) must no longer trip UNJAM, a real stall meeting the classifier evidence (high current with speed below 5.0 rot/s) must still clear, and there should be no repeated stop/go; if stuttering remains, check for repeated `Clearing jam` and inspect the real log. Until that on-robot acceptance is done, only the software fix and local verification are claimed.

## Elastic LED preview

The `LED Preview` tab in `elastic-layout-1027.json` provides color and animation previews independently of real-strip output. To use it, robot code or desktop simulation must be running and Elastic must be connected to that process's NetworkTables; opening the layout alone does not produce preview data.

- The top `LED Pattern` and `LED Idle Effect` controls use the existing setting keys. The large `Current Selection` card previews the selected Pattern (theme Patterns also use the selected Idle Effect); the five fixed cards below show Marigold Bridge / Slow Flow, Festival Night / Breathe, Papel Fiesta / Chase, Alebrije Glow / Slow Flow, and Candle Memory / Static, pairing each theme's distinct palette with its recommended effect for comparison.
- Every card is rendered at a fixed reference brightness and does not read or display real-strip state or actual brightness. `LED Brightness (%)` does not scale the previews, and mechanism actions such as intake, shooting, and eject do not interrupt or replace them.
- These previews compare themes and effects; they do not represent real-strip color or brightness. Screen colors cannot verify physical color order, brightness, power, or section mapping. Previews continue while the robot is `Disabled`; `REPLAY` does not publish these preview topics, so replay does not populate this tab.

## Build & simulation

```bash
./gradlew build          # compile + spotless format check
./gradlew spotlessApply  # auto-format (Google Java Format) — run before committing
./gradlew simulateJava   # desktop simulation (maple-sim physics)
./gradlew replayWatch    # AdvantageKit log replay
./gradlew deploy         # deploy to roboRIO
```

The repository includes a GitHub Actions workflow configured to run `./gradlew build` on push / pull request events; execution depends on whether Actions is enabled for this fork. Complete the build and formatting checks locally before committing.

## Code architecture

- `frc.lib` — team-generic hardware abstraction: `MotorIO` (voltage / velocity / position / torque-current control, with TalonFX and sim implementations), `SensorIO` (CANrange), `MotorSubsystem` base class; IO inputs are logged in **radians** while the subsystem-facing API uses **rotations**.
- `frc.robot.subsystems` — singleton pattern (`public static final mInstance` per subsystem), `X.java` + `XConstants.java` pairs (CAN IDs, gains, sim config).
- `frc.robot.commands` — one folder per command, each with its own `*Constants.java`.
- Runtime mode switches on `Constants.currentMode` (REAL / SIM / REPLAY); each subsystem picks its IO implementation accordingly.
- `elastic-layout-1027.json` — Elastic dashboard layout, kept in sync with the NetworkTables interfaces in code.
