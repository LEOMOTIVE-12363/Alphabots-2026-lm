# 0029 — Startup steer alignment and straight-line heading hold

- Date: 2026-10-28
- Status: Accepted

## Context

The operator reported the robot veering when starting at full stick from rest: after any period of parking or turning, the four steer wheels point wherever the last command left them, and slamming the translation stick drives the chassis while the wheels are still rotating toward the new target (the template's `Module.runSetpoint` issues drive and steer setpoints in the same tick, with only cosine scaling limiting the mismatch). Sim integration confirmed a transient heading veer from tangent (in-place-rotation) initial wheel angles. Separately, open-loop joystick drive has no heading hold: a straight full-speed run drifts in yaw and any disturbance leaves the robot permanently rotated.

A first review round (same day) tightened the gate after line-by-line review found three design flaws in the initial version: rotation-only commands were being gated (manual turn must have absolute priority, including at startup); the gate re-armed on any zero-to-nonzero command edge, so a one-loop zero command mid-drive (stick crossing the deadband during a direction change) dead-stopped a rolling robot; and the gate kept pre-disable state across a disable, so a re-enabled held stick never re-armed.

## Decision

Two independent behaviors, both inside the existing velocity path — no CANcoder offsets, motor gains, deadbands, button layout, NetworkTables keys, or the Elastic layout change:

1. **Startup steer alignment** (`subsystems/drive/StartupAlignGate`, used by `Drive.runVelocity`): the module drive output is held at zero only when a **translation** command (rotation-only never arms) that the caller has **not flagged as manual rotation** (`runVelocity(speeds, allowStartupAlign)`; `joystickDrive` passes false exactly while the right stick is deflected past the deadband, so manual rotation — alone or combined with translation — is never delayed) starts from **measured rest**: the commanded translation must appear on a loop edge while the measured chassis speeds are below `StartupAlignGate.REST_LINEAR_SPEED_MPS = 0.20 m/s` and `REST_ANGULAR_SPEED_RADPS = 0.40 rad/s`. The thresholds are behavioral, not arbitrary: legitimate starts were measured at or below 0.10 m/s / 0.05 rad/s after braking or a disabled coast (≥2× margin), while the direction-change slam enters its one zero-command loop at ~3.4 m/s (17× above) and a 0.5-stick spin runs at ~2 rad/s (5× above). Combining the command edge with the measured rest state rejects both failure modes of either signal alone: an input edge alone re-arms rolling direction changes; measured speed alone would misclassify a brief external push while parked. Once armed, the hold releases when every measured steer angle is within 5 degrees (drive-reversal aware, matching `SwerveModuleState.optimize`; an exactly opposite wheel counts as aligned, driven backwards) of its setpoint, unconditionally after 1.0 s so a failed steer motor cannot wedge the drivetrain, and immediately if the caller's allow flag drops (manual rotation takes over). While the translation command stays active without re-arming, direction changes keep the ordinary cosine-scaled steering with no added wait. `Drive.periodic` calls `startupAlignGate.reset()` while disabled, so a re-enabled held stick is judged against the robot's current (rested) state instead of pre-disable state.

   A zero-speed command targets each module's **last commanded heading** — the WPILib `SwerveDriveKinematics` heading cache, not the currently measured wheel angle — at zero drive speed; wheels already at those headings simply hold their direction while parked, and a wheel still swinging finishes toward that cached target.

2. **Straight-line heading hold** (`DriveCommands.joystickDrive`): a deflected right stick keeps absolute manual rotation priority. With the right stick centered and a translation input present, the gyro holds a target heading through the same `ANGLE` PID/profile constants already tuned for `joystickDriveAtAngle`. The target is set at command (re)start, continuously follows the heading while the right stick is deflected, and re-anchors to the current heading while parked — so releasing the right stick holds the NEW heading (no spring-back), and a shove or pose change while parked never triggers a snap-back on the next push. A parked robot (no translation, no rotation input) commands zero omega and never turns itself. Command restarts after disable and the B heading reset therefore always adopt the current heading, never a stale target.

New read-only log keys: `Drive/StartupAlignHold`, `DriveCommands/HeadingHoldActive`, `DriveCommands/HeadingHoldTargetDeg`. The Turn Speed Limit continues to scale all heading-hold omega through the existing `applyDriveLimits` path.

## Verification

All behavior assertions below failed on the pre-change code for the stated reason before the production change.

- `StartupAlignGateTest` (9 cases) covers the state machine: rotation-only never arms, the manual-rotation flag never arms or holds (and drops an active hold), a translation edge while rolling never arms (the one-loop-zero direction-change flaw), rest-start arming/alignment release, bounded timeout, no mid-run re-arm, `reset()` making a continuing command behave as a fresh start (the disable flaw), and the `optimizedSteerErrorRad` reversal boundary (exactly-opposite wheels count as aligned at error 0, symmetric around 90°, no 2π wrap).
- `TeleopIntegrationTest` integration cases through the real binding and maple-sim physics:
  - `fullForwardFromTangentWheelsHoldsDriveUntilAlignedThenGoesStraight` builds a genuine tangent misalignment (rotation blip; the zero command then targets the already-reached tangent headings) and asserts the robot is held (<0.05 m over the first 160 ms of the ~90° swing), releases within a bound, and drives straight (heading veer was −44.8° ungated).
  - `pureManualRotationFromForwardWheelsIsNotDelayedByStartupAlign` (RED: early |omega| ≈ 3e-169 while held; GREEN: immediate rotation) and `translationWithManualRotationFromTangentWheelsIsNotDelayed` (RED: early |omega| ≈ 1e-75; GREEN: immediate rotation plus translation).
  - `directionChangeAtSpeedDoesNotReArmTheStartupHold` observes the transition directly: with the flaw the robot was dead-stopped at 0.003 m/s at the last loop of a 10-loop window after the slam; the legitimate cosine-scaled transition dips to ~0.08 m/s mid-window and is back above 1 m/s by the window's end — the assertion requires end-of-window speed > 0.5 m/s, on either side of which both states have ≥2× margin.
  - `midDriveDisableThenEnableFromMisalignedWheelsStillAligns` disables mid-rotation, coasts to a verified rest (<0.1 m/s, <0.05 rad/s asserted), and re-enables holding forward: with the stale-state flaw the robot lunged 0.13 m during the steering swing; with the disable reset it is held (<0.05 m) and then drives.
  - Heading-hold cases: manual-turn priority with release-and-hold plus disturbance rejection, parked non-rotation, disable/re-enable target freshness, B-reset target rebasing, red-alliance hold with disturbance.
- Existing regressions stayed green (alliance flip, deadband, Drive/Turn percent scaling, controller routing). One pre-existing test corridor was relocated: `drivePercentScalesSettledForwardSpeed` now teleports to the y = 6 lane because the y = 2 lane grazes the maple-sim lower-left trench wall (top edge y = 1.579 m, x 3.95–5.30 m) once any startup drift takes the bumper edge below y ≈ 2.0; the collision deflection contaminated the settled-speed sample. The assertions are unchanged.
- Full `./gradlew build --offline --rerun-tasks`: 33 suites / 362 tests, 0 failures/errors/skipped (counted from the final JUnit XML). Desktop-sim startup completed with loop-overrun warnings; the 5-degree tolerance, 1.0 s timeout, rest thresholds, and heading-hold feel on the real robot (with its own steer dynamics) still require a robot run.

## Consequences

Full-speed starts go where the stick points instead of where the wheels happened to be pointing, and straight runs plus gentle disturbance correction no longer depend on the driver nudging yaw back. Manual rotation is never delayed — not from rest and not combined with translation. The startup hold adds up to ~0.3 s of perceived latency only when the wheels genuinely start far off target (sim; real steer response differs), and at most the 1.0 s bound in a steer-fault scenario, after which behavior degrades to the previous cosine-scaled drive. Heading hold means the chassis now actively counter-steers yaw disturbances while translating — on the real robot the reused `ANGLE` gains may need retuning, which is a normal AdvantageScope-guided follow-up rather than a contract change.
